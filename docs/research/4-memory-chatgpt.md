# Existing Agent Memory/Graph Systems  
Several open-source and commercial systems now provide persistent memory for AI agents. **Graphiti** (open-sourced by Zep) maintains a *temporal knowledge graph*: it stores **Entities** (with evolving summaries), **Facts** (subject–predicate–object triples tagged with valid-from/to timestamps), and **Episodes** (raw source data that gave rise to each fact). These allow time-based querying and provenance tracking. **Mem0** is a multi-level vector+memory store: it remembers “user preferences” and multi-session facts using a single-pass, *add-only* pipeline. It extracts entities and memory “facts,” embeds them, and supports hybrid retrieval (semantic search, BM25, and entity linking). **Cognee** builds a self-hosted knowledge graph from text, code, and chat: it turns text into entities/relations, code into a symbol-dependency graph, and applies *session distillation* to curate key lessons into lasting memory. Queries use either graph lookups or embedding-based search. **Neo4j Agent Memory** uses a graph-native model with three layers: short-term memory (conversation transcripts), long-term memory (entities, user preferences, facts in a POLE+O graph), and reasoning memory (agent reasoning traces and tool usage). Agents read/write it via the Neo4j Agent Memory SDK.  

Agent-specific features also exist. Claude Code uses **CLAUDE.md** (user-written “project README” prompts) for static instructions, and an *auto-memory* that the model writes from user corrections or preferences. Cursor (the coding IDE) provides *Rules* (`.cursor/rules/`) for always-on context, *Skills* (`SKILL.md`) for on-demand capabilities, and features like plan-mode files (`.cursor/plans/`) and chat references (e.g. `@Chats`) to pull in past context. A hobby tool *Cursor Memory Bank* demonstrates another approach: it defines phases (`/van`, `/plan`, `/build`, etc.) and reads/writes to a shared `memory-bank/` directory. By adaptively loading only phase-relevant rules, it cuts initial tokens by ~70%. Many systems expose memory via APIs or “tools”: for example, Graphiti offers an MCP (Model Context Protocol) server so Claude, Cursor or other MCP-compatible clients can query the graph without changing the agent’s workflow.  

# Do Memory Graphs Improve Code Agents? (Benchmarks & Pitfalls)  
Research on memory benchmarks suggests memory helps *only* when tasks truly exceed a single-context session. In conversational QA benchmarks like BEAM, adding a structured memory can boost accuracy by ~3–13% on 500k–1M token histories, and **over 100% improvement at 10M tokens**, where the dialogue no longer fits in context. In other words, when a developer–agent interaction runs extremely long, external memory drastically helps retain facts and instructions. However, for moderately long conversations that still fit (e.g. <1M tokens), “keeping the full transcript in context can be competitive or better” than using memory. Benchmarks like MemoryArena (ICML 2026) show that systems can answer QA well (as LoCoMo tests) yet still *fail* at downstream tasks if memory is imperfect. MemoryArena found that a memory layer did **not consistently beat** a plain long-context baseline when the history was manageable in one prompt. In practice, this suggests: if your coding session history easily fits in Claude’s window, a sophisticated memory graph may not add value; but if you frequently do multi-day projects or multi-agent workflows, memory will likely pay off.  

Case studies are anecdotal so far. Some vendors report large gains (Cognee cites e.g. 75% answer relevance on one use case), but independent benchmarks are still maturing. Importantly, memory introduces new failure modes. For example, the LongMemEval benchmark highlights that a memory system may “do well on straightforward recall while still failing when facts become stale or the answer is simply not there”. In other words, agents must handle *outdated or missing memories* (e.g. forgetting to update a fact) or they risk confidently giving wrong answers. Security flaws are also documented: recent papers (MINJA, AgentPoison, MemoryGraft) show attackers can inject malicious or false memories via crafted inputs. A single “poisoned” memory can distort the agent later unless there are defenses.  

# Structure-only vs. Full-content Memory (and Privacy)  
If AgentFly only records *structural metadata* (file paths, commands run, hosts, which rule fired, etc.) and omits all text, the agent can learn workflow patterns but loses the actual knowledge. Structure-only memory can track *what happened when* (e.g. “In session 5, files A, B, C were modified in this order and tool `npm run test` was invoked”), and it could hint at which files/areas were important. That might speed up an agent’s orientation (e.g. “I worked on auth flow last time, go check AuthController”). But without content, the agent cannot recall *what* code was there or what parameters were chosen. To answer content-specific queries across sessions (e.g. “What was the algorithm in `foo()` we wrote last session?”), the agent would need to store at least a summary or snippet of the code. Storing content raises privacy/IP concerns: user code or conversation excerpts could contain secrets, internal logic or personal data. Industry guidance emphasizes **sanitizing memory**: e.g. OWASP recommends filtering or encrypting any sensitive data before storage, scoping memory per user, and using time-to-live (TTL) so stale or accidental secrets expire. In short, without storing actual content, you only get a lightweight “breadcrumb trail” of what changed; storing content yields real recall power but risks leaking secrets unless rigorously controlled. AgentFly’s current design (dropping file contents and messages) follows these privacy rules.  

# Graph Schema and Summarization Patterns  
A practical memory graph for AgentFly sessions might include nodes like **Session**, **File/Entity**, **Command**, **Host**, and **Rule**. For example, each session node could connect to file nodes it touched (relation: *edited*), to command nodes it invoked (*used*), and to any rule nodes that fired (*triggered*). Files or code symbols (classes, functions) could also be separate nodes so sessions link to code entities. One could attach lightweight “session summary” metadata (e.g. an automatically generated brief description) to each session node to speed retrieval. Graphiti’s model suggests storing **facts** as timestamped edges: for instance, an edge `(Session)-[edited {from: t1, to: t2}]->(File)` could carry when the edit happened, allowing time-decay (older edits could be deprecated automatically). One might also log “latest owner” or “version” facts for each file to handle updates. For time decay, a simple approach is to drop or down-weight edges older than some threshold (similar to Graphiti’s “invalid-time” handling), ensuring the agent focuses on recent changes. Summarizing a session (e.g. via a short vector or text summary) could also feed a *Session* node attribute, but this requires content and introduces privacy risk. In essence, a useful pattern is **hierarchical context**: project → session → file/command nodes, so a new session can query “What did I last do in module X?”. Graph-based queries (or an embedded vector over the session subgraph) can then feed the agent relevant prior context without exposing full text.  

# Verdict, Use Cases, Experiment & Privacy  
**Feasibility:** *Partly yes.* A cross-session memory graph can benefit long-running or multi-agent coding tasks by preserving context beyond one conversation, but it only outweighs its cost when sessions exceed a model’s context window or when multiple agents share knowledge. For simple, short-lived coding sessions, it adds overhead with little gain. Also, building a robust graph (especially without capturing content) is nontrivial. But for large projects or repeated workflows, it can prevent “reinventing the wheel.”  

**Top Use Cases (Value vs Effort):**  
1. **Project Context Recall (High Value, High Effort):** Persist session summaries, key decisions, and file-changes across days. An agent could recall why a function was implemented or which branch was last modified. *Effort:* Requires designing schema and possibly storing code summaries, handling privacy.  
2. **Multi-Agent Collaboration (High Value, Medium Effort):** Multiple agents (or humans) interact on the same repo. A shared memory graph can link conversations/issues to code. For example, linking GitHub issues, Slack discussions, and agent tasks helps surface relevant past decisions. *Effort:* Involves integrating external data sources and permissions, but less content-heavy than full summaries.  
3. **Environment & Tooling Memory (Medium Value, Low Effort):** Track commands run, environment setups, and tool outputs. E.g. remember that `npm install` was done with pnpm vs npm, or Docker builds/configs. This reduces repetitive setup. *Effort:* Mostly logging and structuring existing actions, no sensitive content, so easier to implement.  

**Minimal Weekend Prototype:** A simple experiment is to log a few coding sessions’ events into a Neo4j or in-memory graph (e.g. session node linking to file and command nodes with timestamps). Then script an agent prompt that queries this graph via an API. For example: “Last week I edited `config.js` and ran `deploy.sh`; remind me what I did.” See if the agent can retrieve useful context (e.g. “You edited the server port in config.js and then ran deploy.sh”). Even without content, this tests the concept. Alternatively, use a memory API (like Mem0 or Cognee) to store and recall a couple of facts across two short sessions (e.g. user preference of npm vs pnpm) and measure if the agent can use it. The point is a lightweight end-to-end loop: record, retrieve, use memory.  

**Privacy Boundary:** AgentFly’s memory must *not* store raw code or conversation text. It should never persist secrets, API keys, or proprietary logic. The system should sanitize all memory entries: drop or hash any credentials, isolate memory per project or user, and set reasonable TTLs to expire old data. The *line not to cross* is content: only abstract structure or sanitized metadata (filenames, command names) should enter the graph. If content ever must be captured (e.g. a code diff summary), it should first be scrubbed of any sensitive tokens and minimized to only what strictly aids future tasks. Following OWASP best practices – input validation, encryption, access controls, and expiration – will help keep memory both useful and safe.
