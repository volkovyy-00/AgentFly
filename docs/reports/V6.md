## 2026-10-18 18:50

### What changed
- `agentfly/recorder/localstore.py` (new): the SQLite history at `~/.local/share/agentfly/history.db`.
  - File mode 600, created before SQLite opens it; a too-open existing file is tightened, a read-only one is left alone. WAL mode, so the `-wal` and `-shm` files inherit 600 (tested).
  - Two tables, only SPEC §4 facts: `sessions(id, workspace_root, started_at, ended_at)` and `steps(session_id, ord, time, kind, tool, verdict, file_path, file_sensitive, command, hosts, rule_id)`, primary key `(session_id, ord)`. `verdict` has a CHECK for the four values `allowed, blocked, warned, highlighted`. A test compares the column list with SPEC §4.
  - One writer thread behind a bounded queue (1024). `enqueue` is a non-blocking put wrapped so it cannot raise. Every item is written in its own transaction with `INSERT OR REPLACE` (same step twice leaves one row) and an upsert of the session row.
  - Any failure is caught per item, logged by exception type only (once per outage), and the connection is reopened at most every 5 s. A store that cannot be opened or written drops items and changes nothing else.
  - Retention: steps older than 28 days, then sessions with no step left, are deleted at start (first thing in the writer thread, so startup is never delayed) and then at most once an hour, also when the recorder is idle. The clock is injectable.
  - Reads: named, parameterised queries on a short-lived `mode=ro` connection with `query_only` and a 2 s progress-handler deadline. A missing file or missing tables read as empty; any other SQLite error is `StoreUnavailable` (503).
  - `wipe_file`: `secure_delete`, delete both tables, checkpoint, `VACUUM`, checkpoint. The checkpoint's busy answer is checked and retried; if it never clears, the CLI says "run it again" and exits 1.
  - `secure_delete=ON` is also set on the writer connection, so retention really removes data from the file (SQLite's default leaves it).
- `agentfly/recorder/api/sessions.py` (new): `GET /api/sessions` (newest first, at most 500) and `GET /api/sessions/{id}/steps` (in order, at most 10 000, with a `truncated` flag). Plain `def` routes, so SQLite runs in a worker thread and never blocks the loop that answers hooks. Unknown id is 404. Step keys are the live trail's keys plus `time` (a test pins that). Registered with `add_api_route` rather than `include_router`: FastAPI 0.142 wraps an included router in a private type that the whitelist test cannot walk.
- `agentfly/recorder/app.py`: lifespan starts and stops the local store; `local_store.enqueue(record)` beside the Neo4j one in `apply_rules`; `neo4j_opt_in()` gates `graph_store.start()`. Session events are handled in `hook()`, right after the JSON check (see "Choices").
- `agentfly/recorder/store.py`: `neo4j_opt_in()` (true only for a real `neo4j = true` in `~/.config/agentfly/config.toml`; missing, broken or non-boolean means off), `first_workspace_root()`, `StepRecord.workspace_root`, and the `file_sensitive` change below. `GraphStore.start` and the Neo4j CLI helpers are unchanged.
- `agentfly/cli/wipe.py` (new) and one import plus one registration line in `agentfly/cli/__init__.py`: `agentfly wipe [--yes]`. It asks first on a terminal; without a terminal and without `--yes` it exits 2. It touches only `history.db`: not `sessions.json`, not Neo4j. With no history file it says so and exits 0 without creating one.
- `demo/scenario.json`: every event has `workspace_roots`.
- Tests: `tests/test_localstore.py`, `tests/test_sessions_api.py`, `tests/test_wipe.py` (new); `tests/test_store.py` (DELETE policy, Neo4j opt-in); `tests/test_app.py` (whitelist and HEAD lines). `memory.py` needed no change.

### Choices I made (for the lead to confirm)
- **"Marked by R1" needed a fix in `build_step_record`.** `rules.mark()` fires on any sensitive word in the raw shell command, but the cleaner turns most arguments into `<arg>` and the builder kept only the first surviving file. So `cat README.md .env`, `cat ~/.aws/credentials`, `cat secrets/id_rsa` and `cat ../other/.env` marked the session but stored `file_sensitive = false`, and a "derived" mark would have shown them unmarked (the demo only reads `.env` through a read event, so the acceptance test alone would not have caught it). Now: a sensitive word that survives cleaning wins as the step's file; one the cleaner hid sets `file_sensitive = true` with no path. Never the basename of a raw token (`API_KEY=x.key` would leak its value). Eight commands are tested against `mark()` itself. Side effect: the live `/api/steps` shows `sensitive: true` on those shell steps. A later mark inherited from a parent chat (D21 A) will not be derivable from steps.
- **Session events are handled in `hook()`, not `apply_rules`** (slightly more than the brief's "one enqueue line", but outside `apply_rules`, which V5a owns). Without it `sessionStart` and friends would become steps and use order numbers. They update only the SQLite session row.
- **The sessionEnd time is when the recorder receives the event.** The real fields of `sessionStart`/`sessionEnd` were never captured (S5 did not see `sessionEnd`), so I read only `conversation_id` and `workspace_roots[0]`. A posted end time wins over the last step's time, as the brief says, so a chat that resumes afterwards shows an end before its newest steps.
- **Workspace root is `workspace_roots[0]` or NULL**, never the recorder's own folder (`project_root_from_payload` falls back to it). Cut at 4096 characters.
- **Rule description is not stored per step**, only `rule_id`; the description is the rule's own text.
- **Neo4j gate is in `lifespan`, not in `GraphStore.start`**, so the four live tests (which I cannot run) are untouched. Anything that calls `start()` itself, or the `--counts` / `--clear` helpers, still connects with whatever credentials it is given.
- **After `agentfly wipe`, a chat that is still running reappears** with its original start time and only its later steps; "marked" is re-derived from those, so it can show unmarked while R1 still blocks (the mark is in `sessions.json`, which wipe does not touch).
- File name `history.db`; WAL mode.

### Final verification
- Simplify pass (four reviewers) applied: the sessions query picks the 500 newest sessions before joining and aggregating, `INSERT OR REPLACE` for steps, `rowcount` instead of two COUNT queries in wipe, one 503 handler, one `enqueue`. Not applied: a set of already-seen sessions (it would go stale after a wipe and drop sessions), batching writes, persisting "marked" (the brief says derive it), moving the Neo4j gate into `start()`, and hoisting the duplicated test helpers into `tests/helpers.py` and `conftest.py` (outside the touch list).
