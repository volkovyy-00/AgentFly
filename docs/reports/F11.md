### What changed

- **`agentfly/recorder/sessions.py`** (the core).
  - `_remember` is the one place a session row is stored. It compares what makes a chat stricter
    (`marked`, `triggers`, `inherited_until`, `inherited_triggers`, `parent_call`, `parent_id`)
    with the old row. A difference bumps `_strict_seq`; anything else only sets `_lazy_dirty`.
    A change to `calls` / `pending` bumps `_links_seq` and `_strict_seq`.
  - `commit()` runs at the end of `observe()` and `put()`. If this hook made something stricter it
    takes the lock, which waits for a write already in flight, and writes itself unless that write
    covered the change. A failed write raises once (a 500, so the client's offline guard applies).
    The next hook that changes nothing is answered from memory and the writer retries.
    `_write_locked` is the only code that writes; it takes its snapshot under the lock.
  - The sequence numbers replace a first-draft shared flag that the writer cleared. With the flag,
    a hook could answer while the writer was still writing its change, or after that write had failed
    (found in the plan review; the tests below catch it).
  - A background writer thread (`start()` / `close()`, `SAVE_DELAY_S` = 10 s) saves the rest.
    A bare `SessionStore(path)` in tests has no thread and saves lazy state on `flush()`.
  - `sweep()` (D29): idle 29 days goes. Kept: a marked chat, a chat with a trigger, one with an open
    inherited mark or trigger window, every parent of a chat that stays, and the calls they point to.
    `load()` gives a note with no (or a damaged) `last_active` the start time, so the first sweep after
    the upgrade drops nothing, also for the hackathon format.
  - `raise_counters()` and a floor for chats with no note; `put` never lowers `next_step` or `last_active`.
  - CR1: `_handed_on()` reads the chat that started a pending Task as it is when the new chat arrives,
    with the record made at the Task as a floor.
  - `save()` writes compact JSON (the C encoder, 3x faster than `indent=2`), `fsync` kept.
- **`agentfly/recorder/localstore.py`**: `next_orders()` (history's `MAX(ord) + 1` per chat, read once
  at start, `{}` and a warning if unreadable) and `read_only()`, shared with `LocalStore._read`.
- **`agentfly/recorder/app.py`**: `lifespan` sweeps, then raises the counters (best effort, a failure only
  logs), starts the writer and the hourly sweeper, and on stop closes the notes first.
- **`agentfly/recorder/rules.py`**: `Session.last_active`.
- **Tests**: new `tests/test_session_state.py` (in-process) and `tests/test_session_kill.py` (a real child
  recorder, SIGKILL and SIGTERM). `tests/test_r0.py` and `tests/test_wipe.py` got one explicit
  `get_store().flush()` each. No other existing test changed.
- **Docs**: AGENTS.md "Testing" (one bullet), SPEC.md §3 ("Where files live") and §5 ("Scope of the mark",
  the fallback sentence).

### Decisions and deviations (none needs a SPEC change)

- **fsync kept** on every `sessions.json` write. Power loss is out of scope, but the strict write is now
  rare, so there was no reason to weaken it.
- A Task start or subagent link writes `links.json` and also `sessions.json`, as `observe` did before. A
  links-only write would be cheaper at 5000 chats (a separate counter pair); I left the protocol as verified.
- The background writer holds the GIL for the length of one `json.dumps` (about 14 ms at 5000 chats), at
  most once per 10 s while a chat is active. The median is unaffected; the p99 of a hook can rise by that.
- D29 reading: the parents of any chat that stays are kept, not only of chats kept by the listed exceptions.
  A superset; it errs strict.
- The step counters come from history's saved rows only. If the history cannot be read at start the
  counters come from `sessions.json`, which can lag the process by up to 10 s (a warning is logged).
- `README.md`, `HOOKS.md` and AGENTS.md "Hook facts" are outside Touches and not edited. They still say the
  session file is written on every hook: `README.md` lines ~269-278, `HOOKS.md` lines 33 and 157, `AGENTS.md`
  "Hook facts" line ~522.
- Not in scope, as the brief says: Neo4j retention and order gaps (D29's known gap), a forget-marks command,
  `_MAX_CALLS`, the hook client.

**`/code-review high` on `main...HEAD`: 7 findings, 3 fixed (`918018c`), 4 not fixed.**
- Fixed: start-up sweep and counter read unguarded (now `best_effort`, a failure only logs); counters raised
  before the sweep, which lost a swept chat's floor (sweep now runs first); `close()` could hang behind a stuck
  write (the last lock wait is bounded by `STOP_WAIT_S`).
- Not fixed, with reasons:
  - `commit()` takes the lock on the loop thread and waits for a write in flight: that wait is the protocol (the
    answer must not go out before the change is durable), it is bounded by one write, and every hook paid it
    before this card.

    rewritten at most every 10 s either way.

    history: **a pre-existing order in `apply_rules`**, unchanged here, and the brief says a failed save answers
    "the same as today". Worth a later card; it is outside this one.
  - Six counters and flags encode "what is owed to disk": a design preference. Two independent reviews of the
    protocol found no flaw, and the tests above break when any piece is removed.
